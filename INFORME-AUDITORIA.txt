================================================================================
1. RESUMEN EJECUTIVO
================================================================================

La aplicacion funcionaba, pero tenia la seguridad basica sin implementar:

  - Las contrasenas se guardaban en texto plano.
  - El secreto que firma los tokens estaba escrito en el codigo, publicado en
    GitHub.
  - NINGUN endpoint pedia autenticacion: cualquiera que conociera la URL se
    descargaba la base de clientes completa.

Se implemento autenticacion real (bcrypt + JWT + guard global), aislamiento de
datos por cuenta y validacion de entrada. Ademas se reestructuro el despliegue
para que UN SOLO servicio de Render sirva tanto la aplicacion web como la API.

Todo quedo verificado en produccion y los datos existentes se conservaron
intactos: 1 usuario, 3 clientes, 3 productos, 52 mensajes.

2. VULNERABILIDADES ENCONTRADAS Y CORREGIDAS
================================================================================

--------------------------------------------------------------------------------
2.1  CONTRASENAS EN TEXTO PLANO                                     [CRITICO]
--------------------------------------------------------------------------------

ANTES
  auth.service.ts comparaba directamente:   user.password !== password
  La contrasena se guardaba tal cual en la columna password.

  Cualquiera con acceso de lectura a la base de datos veia todas las
  contrasenas en claro. Como la gente reutiliza contrasenas, eso compromete
  tambien sus correos y otras cuentas ajenas a esta aplicacion.

AHORA
  Hash bcrypt con 12 rondas. El login usa bcrypt.compare(), nunca comparacion
  directa.

  Cuando el usuario no existe se compara igualmente contra un hash falso, para
  que el tiempo de respuesta no revele que correos estan registrados. Eso evita
  la enumeracion de usuarios por temporizacion.

MIGRACION
  Precisamente porque estaban en claro, se pudieron hashear sin obligar a nadie
  a registrarse de nuevo. Ademas el login detecta una contrasena antigua sin
  hashear y la migra al vuelo en el primer acceso correcto. Nadie pierde el
  acceso.

ARCHIVOS
  backend/src/auth/auth.service.ts
  backend/scripts/hash-passwords.ts   (script de migracion, idempotente)


--------------------------------------------------------------------------------
2.2  SECRETO JWT ESCRITO EN EL CODIGO                               [CRITICO]
--------------------------------------------------------------------------------

ANTES
  auth.module.ts:   secret: 'cj7_ia_secreto_super_seguro'

  Ese texto esta publicado en GitHub. Con el, cualquiera podia FABRICAR un
  token valido para cualquier usuario sin necesidad de contrasena. Era la llave
  maestra del sistema, publicada.

AHORA
  Sale de la variable de entorno JWT_SECRET, y NO tiene valor por defecto: si
  falta, el servidor se niega a arrancar.

  Esa decision es deliberada. Es preferible un servicio caido, que se nota al
  instante, a un servicio que arranca firmando tokens con un secreto que
  cualquiera puede leer.

ARCHIVOS
  backend/src/auth/auth.module.ts
  backend/src/common/env.ts   (helper requireEnv, falla temprano)


--------------------------------------------------------------------------------
2.3  NINGUN ENDPOINT PROTEGIDO                                      [CRITICO]
--------------------------------------------------------------------------------

ANTES
  /clients, /products, /clients/export/csv, /clients/export/vcard: todos
  publicos. Se comprobo contra el servicio real:

      GET https://cj7-ia.onrender.com/clients   ->   HTTP 200, 933 bytes

  Sin token, sin nada. Nombres y telefonos de los clientes servidos a
  cualquiera. Ademas del dano comercial, es una fuga de datos personales.

AHORA
  JwtAuthGuard registrado como guard GLOBAL mediante APP_GUARD. Todo exige un
  Bearer token valido, salvo lo marcado con @Public():

      /health, /auth/login, /auth/register, /whatsapp/webhook

  Comprobado en produccion tras el despliegue:

      GET /clients              ->   401
      GET /products             ->   401
      GET /clients/export/csv   ->   401

DETALLE
  El guard tambien acepta el token por query string (?token=...). Hizo falta
  porque las descargas de vCard y CSV iban por enlace directo, y una etiqueta
  <a href> no puede enviar cabeceras. Al final el frontend paso a usar fetch +
  blob, pero esa via queda soportada.

ARCHIVOS
  backend/src/auth/guards/jwt-auth.guard.ts
  backend/src/auth/decorators/public.decorator.ts
  backend/src/app.module.ts

2.4  SIN AISLAMIENTO ENTRE CUENTAS                                  [CRITICO]
--------------------------------------------------------------------------------

ANTES
  getClients() devolvia TODOS los clientes de la base, sin filtrar por dueno.
  Y como el registro es publico, cualquiera podia crearse una cuenta y ver la

AHORA
  Cada consulta filtra por el userId que viene del token.

  Las modificaciones usan updateMany / deleteMany con { id, userId } en vez de

2.6  WEBHOOK DE WHATSAPP SIN VERIFICAR FIRMA                        [ALTO]
--------------------------------------------------------------------------------

ANTES
  POST /whatsapp/webhook aceptaba cualquier peticion. Un tercero que conociera
  la URL podia inyectar mensajes falsos: llenaba el CRM de contactos inventados
  y, sobre todo, disparaba una llamada a OpenAI por cada mensaje falso. Gasto
  ajeno, factura tuya.

AHORA
  Se valida la cabecera X-Hub-Signature-256 con HMAC-SHA256 contra
  META_APP_SECRET, usando timingSafeEqual para no filtrar informacion por el
  tiempo de comparacion.

  Necesita el cuerpo crudo de la peticion, sin parsear. Por eso main.ts crea la
  aplicacion con { rawBody: true }.

COMPORTAMIENTO SEGUN EL VALOR DE META_APP_SECRET

  VACIO       El webhook acepta todo, pero deja un aviso en los logs.
              Es intencionado: permite desplegar sin romper el servicio
              mientras se termina de configurar Meta.

  CORRECTO    Funciona y ademas protege.

  INCORRECTO  RECHAZA TODOS LOS MENSAJES con 403 y el agente deja de
              responder.

  El tercer caso ocurrio de verdad durante el despliegue: se habia quedado el
  texto de ejemplo "PEGA_AQUI_TU_APP_SECRET" en la variable. Es la primera
  cosa que hay que mirar si el agente de WhatsApp deja de contestar.

ARCHIVOS
  backend/src/whatsapp/whatsapp.service.ts   (metodo verifySignature)
  backend/src/whatsapp/whatsapp.controller.ts
  backend/src/main.ts

2.9  SIN VALIDACION DE ENTRADA                                      [ALTO]
--------------------------------------------------------------------------------

ANTES
  Los controladores aceptaban cualquier objeto JSON tal cual y se lo pasaban a
  Prisma. Sin longitudes maximas, sin comprobacion de formatos, sin filtrado de
  campos.

AHORA
  ValidationPipe global con DTOs de class-validator:

      whitelist              descarta las propiedades no declaradas en el DTO
      forbidNonWhitelisted   y ademas responde 400 si llegan
      transform              convierte tipos segun el DTO

  El whitelist cierra de paso una escalada de privilegios: antes se podia
  enviar {"role":"ADMIN"} en el registro y crearse una cuenta administradora.
  Comprobado en produccion:

      POST /auth/register  con {"role":"ADMIN", ...}
      ->  400  "property role should not exist"

2.10  INYECCION DE FORMULAS EN EL EXPORT CSV                        [MEDIO]
--------------------------------------------------------------------------------

ANTES
  Los campos se concatenaban entre comillas sin escapar nada.

  Un cliente cuyo nombre empiece por = + - o @ se convierte en codigo
  EJECUTABLE al abrir el CSV en Excel o Google Sheets. Un nombre como
  =HYPERLINK(...) puede exfiltrar el contenido de la hoja.

AHORA
  csvField() duplica las comillas y antepone un apostrofo a cualquier valor que
  empiece por = + - @ tabulador o retorno de carro, que son los caracteres que
  Excel interpreta como inicio de formula.

  Se anadio ademas el BOM UTF-8 para que Excel abra bien los acentos.

ARCHIVOS
  backend/src/common/csv.ts
  backend/src/client/client.controller.ts

3. BUGS FUNCIONALES CORREGIDOS
================================================================================

3.1  EDITAR UN PRODUCTO NUNCA FUNCIONO
     El frontend hacia PUT /products/:id, pero ProductController solo tenia
     @Get, @Post y @Delete. Siempre respondia 404.
     Se anadio @Put(':id'), con soporte para reemplazar la imagen: si no se
     sube una nueva, se conserva la anterior.

3.2  EL BUILD DE PRODUCCION SE ROMPIA EN SILENCIO
     Al anadir la carpeta scripts/, TypeScript paso a tener dos raices y
     empezo a emitir dist/src/main.js en vez de dist/main.js. El comando de
     arranque node dist/main no encontraba el punto de entrada.
     Corregido excluyendo scripts/ en tsconfig.build.json.
     Este habria roto el despliegue en Render sin dar una pista clara.

3.3  CUATRO POOLS DE CONEXIONES A POSTGRES
     Cada servicio hacia new PrismaClient(). En los planes gratuitos de
     Supabase y Render eso agota el limite de conexiones.
     Ahora hay un PrismaService unico, expuesto en un modulo @Global.

3.4  LA TABLA DE CLIENTES ESTABA DESCUADRADA
     La cabecera declaraba 7 columnas (Nombre, Contacto, Etiquetas, Estado,
     Registro, Acciones) pero cada fila solo pintaba 5: faltaban las celdas de
     Estado y Registro. Anadidas.

3.5  next/image HABRIA FALLADO EN PRODUCCION
     Las fotos de producto vienen de Supabase, un host externo, y
     next.config.ts estaba vacio, sin images.remotePatterns. En produccion eso
     lanza "hostname is not configured". La vista previa local usa ademas una
     URL blob:, que tampoco puede optimizarse.
     (Con la exportacion estatica posterior se resolvio con unoptimized.)

3.6  CARRERA AL ASIGNAR clientCode
     El codigo hacia "buscar el ultimo y sumar 1" sin transaccion, sobre una
     columna @unique. Dos registros simultaneos pedian el mismo numero y uno
     fallaba. Ahora se reintenta hasta 5 veces ante el error P2002 de Prisma.

3.7  RESPUESTAS DUPLICADAS DE LA IA EN WHATSAPP
     El servidor confirmaba a Meta DESPUES de llamar a OpenAI. Si tardaba mas
     de la cuenta, Meta reenviaba el mismo mensaje y la IA respondia dos veces,
     cobrando dos llamadas.
     Ahora responde 200 de inmediato y procesa despues.

3.8  DOS CAIDAS TOTALES POR DEPENDENCIAS EXTERNAS
     StorageService creaba el cliente de Supabase en el constructor, y
     AiService el de OpenAI. Si cualquiera de los dos lanzaba una excepcion,
     Nest no podia instanciar el modulo y se caia la aplicacion ENTERA: login,
     CRM, inventario, todo.

     Esto ocurrio de verdad en el primer despliegue:

         Error: Node.js detected but native WebSocket not found.
           at new RealtimeClient (...)
           at new StorageService (dist/storage/storage.service.js:26)
         ==> Exited with status 1

     @supabase/supabase-js necesita el WebSocket global, que no existe hasta
     Node 22. En local no se noto porque ahi corre Node 24.

     Ahora ambos clientes se crean al primer uso. Un fallo de almacenamiento o
     de OpenAI degrada solo esa funcion concreta, y devuelve un error util en
     vez de impedir el arranque.

     OJO: este arreglo esta en la rama, NO en produccion. La caida se resolvio
     subiendo NODE_VERSION a 22 a mano en Render. Ver seccion 15.

3.9  TELEFONOS DUPLICADOS CON DISTINTO FORMATO
     "+591 700-11223" y "59170011223" se guardaban como dos clientes distintos.
     Ahora se normaliza a solo digitos antes de guardar.

3.10 EFECTOS DE REACT QUE LEIAN localStorage
     El codigo original usaba setTimeout(..., 0) dentro de useEffect para
     esquivar el aviso del compilador de React sobre setState en efectos.
     Sustituido por useSyncExternalStore, que es el mecanismo previsto para
     estado externo a React y ademas resuelve bien la hidratacion en servidor.

4. CAMBIOS DE ARQUITECTURA
================================================================================

--------------------------------------------------------------------------------
4.1  DE DOS SERVICIOS A UNO
--------------------------------------------------------------------------------

Peticion expresa: manejar todo en un unico Web Service de Render.

COMO FUNCIONA
  El frontend se compila a HTML estatico (output: "export" en next.config.ts) y
  NestJS lo sirve desde frontend/out como archivos estaticos.

POR QUE ES VIABLE
  Las 8 rutas de la aplicacion son estaticas. Cada pagina es "use client" y
  pide los datos desde el navegador, asi que no hay renderizado en servidor que
  perder.

VENTAJAS
  - Un solo servicio en el plan gratuito
  - Un solo arranque en frio en vez de dos
  - CORS deja de ser un problema: mismo origen
  - Una sola URL para todo

DETALLE CRITICO: trailingSlash
  Sin trailingSlash: true, Next genera un directorio "login/" (con sus payloads
  internos) JUNTO a "login.html". Cualquier servidor de estaticos entra al
  directorio, no encuentra index.html dentro y responde 404.
  Con trailingSlash genera out/login/index.html, que es lo que espera cualquier
  servidor estatico.

RESOLUCION DE LA CARPETA DEL CLIENTE
  main.ts calcula la ruta desde __dirname (backend/dist), NO desde
  process.cwd(), porque Render arranca el proceso desde la raiz del repositorio
  y cwd no es fiable.

ORDEN DE RUTEO
  1. Middleware de archivos estaticos, con extensions: ['html']
  2. Rutas de la API de Nest
  3. Middleware final: si es GET, acepta text/html y la ruta no empieza por un
     prefijo de la API, devuelve el 404.html del cliente

  API_PREFIXES = /auth  /clients  /products  /whatsapp  /health  /socket.io

helmet SIN CSP
  La Content-Security-Policy por defecto de helmet bloquea los scripts que
  genera Next. Se desactiva solo esa parte; el resto de cabeceras siguen
  activas.


--------------------------------------------------------------------------------
4.2  CLIENTE HTTP UNICO EN EL FRONTEND
--------------------------------------------------------------------------------

ANTES
  La URL "https://cj7-ia.onrender.com" estaba escrita a mano en 13 sitios
  repartidos por 4 archivos. Era imposible apuntar a un backend local sin
  editar codigo, y cambiar de dominio significaba tocar 13 lineas.

AHORA
  frontend/lib/api.ts centraliza todo:

  apiFetch()
    Anade el Bearer token, serializa JSON o FormData segun corresponda, extrae
    los mensajes de error de Nest (incluido el ARRAY que devuelve la
    validacion), y ante un 401 limpia la sesion.

  apiDownload()
    Descarga archivos protegidos como blob, porque una etiqueta <a href> no
    puede enviar la cabecera Authorization.

  NEXT_PUBLIC_API_URL vacia significa "mismo origen". Solo hace falta definirla
  en desarrollo, donde el frontend corre en :3000 y el backend en :8765.


--------------------------------------------------------------------------------
4.3  LA SESION COMO ESTADO EXTERNO DE REACT
--------------------------------------------------------------------------------

frontend/lib/auth.ts expone el token y el usuario mediante useSyncExternalStore,
con un conjunto de suscriptores propio mas el evento "storage" del navegador
(que avisa de cambios hechos en OTRA pestana: si se cierra sesion en una, las
demas se enteran).

El snapshot se cachea por el texto crudo del localStorage. Esto es obligatorio,
no una optimizacion: getSnapshot debe devolver la MISMA referencia mientras el
valor no cambie, o React entra en un bucle infinito de renders.

Esto permite ademas que la redireccion tras un 401 la haga el router de Next en
vez de window.location: apiFetch solo borra la sesion, el store avisa, y
app/dashboard/layout.tsx redirige.


--------------------------------------------------------------------------------
4.4  PROTECCION DEL PANEL EN UN SOLO SITIO
--------------------------------------------------------------------------------

frontend/app/dashboard/layout.tsx cubre /dashboard y todas sus subrutas, asi que
ninguna pagina tiene que acordarse de comprobar la sesion por su cuenta.

IMPORTANTE: es una comprobacion de EXPERIENCIA DE USUARIO, no de seguridad.
Quien manda es el JwtAuthGuard del backend. Aunque alguien fuerce la ruta en el
navegador, no vera ningun dato porque la API rechazara sus peticiones.

CAMBIOS YA APLICADOS A LA BASE DE PRODUCCION

Antes de aplicar nada se previsualizo el SQL con "prisma migrate diff".
Resultado: CERO operaciones destructivas. Ni DROP TABLE, ni DROP COLUMN, ni
cambios de tipo. Solo indices y claves foraneas.

  User.role      el valor por defecto pasa de "ADMIN" a "USER"
  Client.phone   deja de ser @unique global; ahora @@unique([userId, phone])
  Product.sku    deja de ser @unique global; ahora @@unique([userId, sku])
  Indices        [userId, createdAt] en Client y Product
                 [phone, createdAt] en Message
                 [clientId] en Sale
  Foraneas       onDelete: Cascade

POR QUE LA UNICIDAD PASA A SER POR CUENTA
  Con multiples cuentas, que un telefono sea unico en TODA la base significa
  que si un negocio registra a un cliente, ningun otro negocio puede tenerlo.
  Dos empresas distintas pueden compartir cliente, y desde luego pueden usar el
  mismo codigo SKU.

MODELOS

  User      id, email(unico), username(unico), password(hash bcrypt), fullName,
            gender, clientCode(unico), bio, role, createdAt
            relaciones: clients[], products[]

  Client    id, name, phone, email, tags[], status, notes, lastContact,
            createdAt, userId
            relaciones: user, sales[]

  Product   id, name, description, category, sku, price, offerPrice, cost,
            stock, minStock, imageUrl, status, createdAt, userId
            relaciones: user

  Sale      id, total, status, createdAt, clientId
            relaciones: client

  Message   id, phone, sender("user" o "ai"), content, createdAt

NOTA IMPORTANTE
  Message NO tiene userId. Los mensajes de WhatsApp no estan aislados por
  cuenta. Hoy no es un problema porque solo hay un usuario, pero conviene
  resolverlo antes de abrir el registro a mas negocios.

13. LO QUE QUEDA PENDIENTE
================================================================================

SEGURIDAD

  - El campo role existe pero NADA lo comprueba. No hay autorizacion por rol:
    un USER puede exactamente lo mismo que un ADMIN.
  - El token vive en localStorage, legible por cualquier XSS. Lo correcto seria
    una cookie httpOnly con SameSite, y refresh tokens.
  - No hay recuperacion de contrasena.
  - No hay verificacion de correo: cualquiera puede registrarse con un email
    que no es suyo.
  - Message no esta aislado por cuenta (ver seccion 6).
  - El registro es publico. Si el producto es para un solo negocio, deberia
    cerrarse o pasar a un sistema de invitaciones.

FUNCIONALIDAD INCOMPLETA (maquetas con datos fijos)

  - Panel: "$12,450", "34 ventas", "82% conversion" estan escritos a mano en el
    codigo, no salen de la base de datos.
  - Pipeline de ventas: tarjetas de ejemplo ("Juan Perez", "Ana Lopez").
  - Modulos Ventas, Meta Ads IA y Analitica: botones sin destino.
  - El modelo Sale existe en el esquema pero ningun endpoint lo usa.
  - QueueModule (BullMQ) sigue comentado en app.module.ts.
  - generateAdImage() esta implementado pero no expuesto en ninguna ruta.

CALIDAD

  - No hay tests. app.controller.spec.ts es el de ejemplo que trae Nest.
  - tsconfig tiene strictNullChecks: false y noImplicitAny: false.
  - Prisma 5.22 con la version 8.x ya disponible.

OPERACION

  - Sin logs estructurados ni monitorizacion de errores (Sentry o similar).
  - Sin copias de seguridad automaticas de la base de datos.
  - Plan gratuito: el servicio se duerme a los 15 minutos.

DATOS

  - Hay erratas en el catalogo que la IA REPITE literalmente a los clientes,
    porque tiene instrucciones de no inventarse nada:

        "Zapatillzas ARG xxi"   ->  deberia decir "Zapatillas"
